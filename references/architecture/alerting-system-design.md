# Method Alerting System — Design

> A curated, SLO-driven alert set where **every page is urgent, important, actionable, and real.**
> This is a **separate track** from the triage-bot's `escalation_score` machinery: the bot builds the KB and
> investigates; this *applies those learnings* to a small set of genuinely good alerts. Source of truth for the
> rules is [`kb/slo-catalog.json`](../../kb/slo-catalog.json); they are generated by
> [`scripts/gen_grafana_alerts.py`](../../scripts/gen_grafana_alerts.py) into [`alerting/grafana/`](../../alerting/grafana)
> and provisioned by [`scripts/grafana_provision.py`](../../scripts/grafana_provision.py).

## Context

Method's alerts today are cause-level and noisy. The worst offender, `ki-2026-05-21-gateway-microservices-timeout`
(ki-21), has fired **430×** and is permanently suppressed; `ki-2026-05-24-runtime-core-rtc-p95` (ki-24) **172×**.
This design replaces noise with a handful of symptom-level SLO alerts.

**Two standing constraints:**
- **No `@`-mentions** of any person/user-group. Owning teams are named as **inert text** in alert annotations
  (matches `prompt.md` Hard Rule #13).
- **All notifications post to `#triage-bot-health`** for now via one Slack contact point. Per-team
  `TeamSlackAlertChannel` webhooks are the documented eventual target; a Grafana **XMatters** contact point already
  exists for eventual P1 paging — used **only** after this system demonstrates value and the user authorizes it.

## Platform (verified live, 2026-06-17)

**Grafana Enterprise 12.0.1** at `grafana.method.me` (also reachable as `logstash3.method.me/grafana`) is the alert
control plane. It already runs **40 alert rules + 13 contact points** and has the datasources we need:

| Signal | Grafana datasource | Type |
|---|---|---|
| Screen-load / action p95 (ki-24) | `rtcapi_metrics`, `rtcapi_account_metrics` | InfluxDB |
| Action / AppRoutine | `approutine_action_metrics`, `approutine_metrics` | InfluxDB |
| EDA / RabbitMQ (subscriber lag, DLQ) | `eda_metrics` | InfluxDB |
| QBO / sync backlog | `syncservice_metrics` | InfluxDB |
| App logs / errors | `applogs-es`, `Elasticsearch` | Elasticsearch |
| (gateway latency — to confirm) | `Prometheus` | Prometheus |

**No Datadog datasource exists or is needed** — Datadog stays as native Slack alerts the bot reads. House query
style is **InfluxQL** + ES Lucene. Our rules go in a dedicated **`SLO` folder** so they never collide with the 40
existing rules. The provisioner is the **only sanctioned write tool** in this repo and talks **only to Grafana**
(it reads InfluxDB/ES/Prometheus *through* datasources — it never mutates Datadog/ES, so `prompt.md` Hard Rule #3 is
untouched).

## Design stance (and tensions resolved)

- **Symptom, not cause** (Google SRE / Ewaschuk): page on user-visible SLO burn at the edge; cause signals →
  dashboards. **Two justified cause exceptions:** `subscriber-heartbeat` (F1) and `rabbitmq-dlq-nonzero` (F2) — proven
  leading indicators with silent user impact and no symptom-level detector.
- **Four Golden Signals + RED/USE**: RED per journey at the edge; USE for resources on dashboards.
- **SLI → SLO → alert**: nothing fires that isn't a row in `kb/slo-catalog.json`.
- **Multi-window, multi-burn-rate** off error budgets where volume supports it; **absolute-count** fallback where it
  doesn't (designer save, QBO backlog, DLQ, heartbeat).
- **CASE** on every rule (Context-rich, Actionable, Symptom-based, Evaluated).

**Tensions:** (1) static thresholds with no budget context caused ki-21's 430 fires → we use budget-burn for
high-volume journeys, absolute thresholds only for low-volume ones. (2) symptom purity vs the two F1/F2 cause alerts —
resolved in their favour because nothing else detects them. (3) coverage vs volume — deliberately under-cover (8 SLOs,
17 rules, only fast-burn pages); ki-21's raw XHR monitor is **retired**, folded into SLO-2/3. (4) `<200ms` aspirational
vs `<3s` operational latency — SLO threshold is **p95 < 3s** (ki-24 evidence: 5–13s breaches); 200ms stays a dashboard
goal.

## Deliverable 1 — Signals inventory
| Journey | Signals | Measurement | Datasource |
|---|---|---|---|
| Sign-in / auth | Errors, Duration | auth-failure log ratio | `applogs-es` |
| Gateway health | Rate, Errors, Duration | non-5xx ratio at Ocelot edge; p95 | `applogs-es`; p95 `Prometheus` (TBC) |

| QBO sync | Errors, Saturation | sync-failure ratio; backlog age | `syncservice_metrics` |
| Async / cache-invalidation | Saturation, Errors | heartbeat; consumer lag; DLQ | `eda_metrics` |

Cause signals (CPU, IIS state, Redis hit-rate, SQL skew, raw queue depth) → **dashboards only** (Deliverable 6).

## Deliverable 2 — SLI / SLO specification
30-day window (43,200 min). See [`kb/slo-catalog.json`](../../kb/slo-catalog.json) for the machine-readable form.

| # | SLI (good ÷ valid) | Target / window | Datasource |
|---|---|---|---|
| SLO-1 Sign-in | successful auth ÷ all attempts | 99.9% / 30d | `applogs-es` |
| SLO-2 Gateway availability | non-5xx ÷ all gateway reqs | 99.95% / 30d | `applogs-es` |
| SLO-3 Gateway latency | p95 ≤ 800ms | 99% of windows / 30d | `Prometheus` (confirm) |
| SLO-4 Screen load | non-error & p95 ≤ 3s ÷ all loads | 99.9%, p95<3s | `rtcapi_metrics` + `applogs-es` |
| SLO-5 Action execution | non-error & p95 ≤ 5s ÷ all actions | 99.9%, p95<5s | `rtcapi_metrics`/`approutine_action_metrics` + `applogs-es` |
| SLO-6 Designer save | 2xx ÷ all saves | 99.9% / 30d | `applogs-es` |
| SLO-7 QBO sync | completes <15m ÷ all jobs | 99% / 30d | `syncservice_metrics` |
| SLO-8 Cache-invalidation (F1) | Subscriber alive & lag<100 | 99.9% / 30d | `eda_metrics` |

Dashboard goals (not SLOs): screen-load p95 200ms; Redis cache-hit >95% (F8); SQL cluster variance <1.5× (F3).

## Deliverable 3 — SLO alerting table (multi-window, multi-burn-rate)
Burn = observed_error_rate ÷ (1 − target). **Only fast-burn pages.** All → `#triage-bot-health`.

| Tier | Condition (long **and** short window) | Severity / action |
|---|---|---|
| Fast | ≥ 14.4× over 1h **and** 5m | P1 page-equivalent |
| Fast (slower) | ≥ 6× over 6h **and** 30m | P1 page-equivalent |
| Slow | ≥ 3× over 24h **and** 2h | P2 ticket |
| Drift | ≥ 1× over 3d | P2/FYI |

Both windows must breach (precision); the short window is the reset/confirmation gate (kills flapping; single
synthetic-run failures never page). The ladder lives in `kb/slo-catalog.json → meta.burn_ladder` and is expanded by
the generator into Grafana rules (ES single-bucket count → `reduce` → `math` burn ratio → `threshold` condition).
Latency SLOs use InfluxQL `percentile("…",95)` thresholded at 3000/5000ms; gateway p95 uses PromQL `histogram_quantile`.

`B063S8NBW0M`; (5) `ms-search-api` vs `Method.Search` alias ambiguity. See `kb/slo-catalog.json → ownership_gaps`.

## Deliverable 6 — What we deliberately did NOT alert on
Demoted to dashboards/runbooks: host CPU/memory; IIS pool recycles (F6 — symptom is gateway 503 = SLO-2); **Redis
cache-hit (F8)** (overrides F8's "alert <95%" — the latency SLO catches user impact); SQL cluster skew (F3, monthly);
raw RabbitMQ queue depth (except the two leading-indicator alerts); individual log/exception keywords (the bot's KB
territory); **ki-21's raw XHR monitor #77419271** (430 fires, retired → folded into SLO-2/3); single synthetic-run
failures (need multi-window SLO-1 confirmation).

## Deliverable 7 — Operational hygiene
Fold an "Alerting health" phase into the existing **monthly stability-review** routine: per team, report which alerts
fired, % actioned, which flapped, and a tune/keep/delete call. Upkeep owner = response owner. Zero actioned fires in
60d = delete candidate. **Meta-metrics:** pages/on-call-shift (<2), % pages actioned (>90%), MTTA, false-positive rate
(<5%). Reuse `references/methodology/metrics-formulas.md` for availability/MTTR/burn math.

# Runbooks

Each SLO alert links here. A runbook starts the investigation; it never says "ack and watch."

<a id="rb-slo-1"></a>
## rb-slo-1 — Sign-in availability (owner: Admin)
Symptom: new logins failing. **First:** is `gateway-avail` also firing? If yes, treat as the gateway incident
(parent). **Check:** `ms-authentication-api` health, Redis JWT cache hit-rate dashboard (F8 — a cache-miss storm
overwhelms auth), recent deploys (`git log` on ms-authentication-api/ms-gateway-api), ES `applogs-es` auth errors.
Existing JWTs survive ~1h, so brief blips are tolerable; sustained burn is not.

<a id="rb-slo-2"></a>
## rb-slo-2 — Gateway availability (owner: Admin)
Symptom: 5xx at the edge — the whole stack is unreachable when severe. This is the **parent**: while it fires, SLO-3/4/5
child alerts are suppressed. **Check:** runtime-core IIS pool state (F6 — a stopped pool 503s everything), gateway →
Redis (F8), recent gateway/auth deploys. Dashboards: gateway RED, IIS pool, Redis. ki-21 (Ocelot timeouts to
microservices) is the historical recurring cause.

<a id="rb-slo-3"></a>
## rb-slo-3 — Gateway latency (owner: Admin)
Symptom: edge p95 > 800ms. Usually Redis degradation (F8) or a downstream microservice tail. **Check:** Redis health,
`microservices` IIS pool recycle correlation, gateway p95 by route. Inhibited while gateway-avail fires.

<a id="rb-slo-4"></a>
## rb-slo-4 — Screen runtime load (owner: Vertical App Experience — see ownership gap)
Symptom: screens slow/erroring; RTC screen-load p95 > 3s. This is ki-24's signal. **Check:** runtime-core RTC dashboard
(`rtcapi_metrics`), Redis backpressure, `microservices` pool restart correlation, SQL cluster latency for the affected
tenants. Latency-only with 0 errors often = shared upstream (co-fires with gateway/Redis).

<a id="rb-slo-5"></a>
## rb-slo-5 — Action execution (owner: No Code Next Gen)
Symptom: actions failing or p95 > 5s. **Check:** action-execution dashboard (`approutine_action_metrics`), RabbitMQ
consumer health (slow consumers stall actions), SQL write latency, recent runtime-core/actions deploys.

<a id="rb-slo-6"></a>
## rb-slo-6 — Designer save (owner: No Code Next Gen)
Symptom: ≥5 save failures in 30m — designers losing work. **Check:** Designer.Core.Api errors in `applogs-es`,
last-write-wins concurrency (F5), recent designer deploys. Low-volume journey: absolute count, not burn-rate.

<a id="rb-slo-7"></a>
## rb-slo-7 — QBO sync freshness (owner: Connect)
Symptom: oldest unprocessed sync > 30m — QBO data stale. **Check:** `syncservice_metrics` backlog dashboard, RabbitMQ
queue depth for sync, qbo-sync-api health/errors, QBO API status.

<a id="rb-slo-8"></a>
## rb-slo-8 — Cache-invalidation timeliness / Subscriber (owner: CRM Experience)
**Justified cause alert (F1).** Symptom: `Runtime.Core.Subscriber` stopped → cache invalidation halts → users see
stale screens for minutes with NO error-rate signal. `subscriber-heartbeat` (P1) fires on no heartbeat in 5m;
`rabbitmq-consumer-lag` (P2) on lag > 100 for 5m (suppressed while the heartbeat alert fires). **Check:** Subscriber
process/host, RabbitMQ consumer state, restart the consumer; verify cache keys (`runtime-core:2:`) invalidate.

<a id="rb-f2"></a>
## rb-f2 — RabbitMQ dead-letter queue (owner: Connect)
**Justified cause alert (F2).** Symptom: DLQ depth > 0 for 15m — events dead-lettering silently; AppRoutines stall.
**Check:** which queue's DLQ, the consumer that's failing (downstream timeout/deadlock/slow query), `eda_metrics`
dashboard. Drain/replay after the root consumer is fixed.

## How to operate this (provisioning workflow)
1. Add `GRAFANA_URL` (verified `https://grafana.method.me`, or `https://logstash3.method.me/grafana`) and a
   `GRAFANA_TOKEN` (service-account, alerting + datasources RBAC) to `.env`. Token is preferred over the SSO password.
2. `python scripts/grafana_provision.py probe` — resolve the `🔎` field names (InfluxDB measurements/fields, gateway
   p95 in Prometheus) and update `kb/slo-catalog.json` accordingly.
3. `python scripts/gen_grafana_alerts.py` — regenerate `alerting/grafana/*.json`.
4. `python scripts/grafana_provision.py apply` — **dry-run by default** (prints create/update + any unresolved
   datasource); add `--commit` to write into the `SLO` folder.
5. `python scripts/grafana_provision.py contact-point-ensure --commit` (with `TRIAGE_BOT_HEALTH_WEBHOOK` in env) to
   create the Slack contact point, then `test-fire --commit` to confirm delivery — **no `@`-mentions**.
6. Review as a PR; never let the set mutate silently.

**Closing the loop with the bot:** when the KB marks a known-issue resolved/mitigated, regenerate and retire the
matching SLO rule. The bot still never tags teams and still posts only to `#triage-bot-health`.
