### F3 — Monitor 77419271 fires solo on single-user Angular `$digest` floods

**Symptom (one line):** A single user with one bad navigation can trip the per-account 40-error / 5-min threshold of monitor 77419271 because the digest loop generates 40+ identical errors from one `TypeError`; the monitor's grouping is per-account, not per-error-class.

**Frequency:** Co-located with F1; surfaces every time F1 (or any future analogous bug) trips. In the window: ≥ 24 fe-errors `needs-human` clusters tagged to this monitor.

**Triage-bot evidence:**
- Monitor query text (above) — no group-by on `@error.message`; the existing exclusion list (`-*ResizeObserver* -*signalr* -*mixpanel* -*hotjar*`) treats specific patterns as noise but does not normalize for digest-amplified single-bug duplication.
- 5 of the 8 named-account top hits in the F1 DD aggregation are single-user (`user_identity` distinct from the others) — confirming the per-user / per-digest amplification shape.
- The investigation explicitly recommends `group_by error.message` tuning (`docs/investigations/2026-05-21-515f5ee521d61ac4.md` Lessons §3).

**Fresh DD evidence:** see F1.

**Trend-delta:** N/A — the monitor's behavior has been steady; the trend is in the bugs that trip it, not the monitor itself.

**Five-whys:** Compressed (4 whys; structural cause reached at why 4):

```
Symptom: 24+ consecutive triage cycles surface fe-errors needs-human DMs for monitor 77419271.

Why 1: One user can solo-trip the monitor.
  Evidence: F1 DD aggregation showing 9-hit per-account counts that include single user_identity.

Why 2: The monitor groups by @account_name, sums error count, applies a 40/5min threshold,
  with no normalization for duplicate errors.
  Evidence: monitor query text above.

Why 3: The error stream from `isUsingControl` (and analogues) is amplified by the Angular $digest
  loop — one failed page load yields dozens of identical errors.
  Evidence: investigation; DD logs (identical timestamps within seconds).

Why 4: The monitor was configured to detect anomalous user-impact (account-level threshold) but
  not duplication-resistant (no per-message dedup). Structural: the threshold model and the
  shape of the data are mismatched — the threshold reads "40 unhappy users" but the data
  delivers "1 user × 40 errors".
  Evidence: monitor query has no count_distinct or by @error.message clause.

Stop: structural mismatch between threshold semantics and data shape.
```
