### F2 — Phase 0d data-adequacy check silently miscounts in-window lines (10× undercount)

**Symptom (one line):** `playbooks/stability-review.md` Step 0 prescribes an `awk` script for the Phase 0d data-adequacy check whose regex `/"ts":[ ]?([0-9]+)/` only matches **numeric** `ts` fields; recent triage entries use **ISO-string** `ts` ("2026-05-20T20:23:13Z"). This run's prescribed check returned **16 in-window lines**; the actual count by JSON-parsing is **1,480** (92× higher). Had the actual count been any lower than 10, the routine would have exited "skipping — need ≥10".

**Frequency:** Affects every future run of the routine until the playbook is fixed. Did not affect prior reports (2026-05-05/06/07) because they ran on a much shorter incident-log where most entries were still numeric `poll-cycle` records; the gradual migration to ISO-string `ts` (driven by the routine itself when it began emitting events from its triage cycles instead of heartbeats) made the regex go stale.

**Triage-bot evidence:**
- Run of the prescribed `awk` on the current `kb/incident-log.jsonl`: `LINES_IN_WINDOW=16` (would proceed but flag "Limited data" per Step 0).
- Python JSON-parsed re-count (accepting both numeric and ISO `ts`): `IN-WINDOW LINES: 1480` (Classifications: needs-human=315, grouped=947, poll-cycle=172, heartbeat=27, deduplicated=16, stability-review=3).
- Sample mismatched entry: `kb/incident-log.jsonl` L1480 has `"ts": "2026-05-20T21:24:30Z"` (string); L1370 has `"ts": 1779249945` (number). Both are valid in the same file.

**Fresh DD/ES evidence:** N/A (this is a routine bug, not a DD-monitored service).

**Phase 3c request-id pivot:** N/A.

**Five-whys:**

```
Symptom: The Phase 0d data-adequacy check undercounts by 92× and would falsely exit
  if the actual count happened to be in the 10-15 range.

Why 1: The awk regex /"ts":[ ]?([0-9]+)/ requires a numeric value after the colon.
  Recent triage entries serialise ts as an ISO-string with quotes ("2026-05-20T…Z").
  Evidence: grep -c '"ts": "' kb/incident-log.jsonl → 1,266 hits; grep -c '"ts": [0-9]'
  → 224 hits. The string form dominates.

Why 2: The playbook was authored when the incident-log only contained heartbeats and
  stability-review entries (which serialize ts as Unix epoch). The triage routine then
  began emitting needs-human / grouped / poll-cycle entries using ISO-strings (matching
  the convention in docs/investigations/<date>-<hash>.md filenames).
  Evidence: First ISO-ts entry is around line 583 (2026-05-14T12:08Z); first numeric-ts
  entry is much earlier in the file. The schema split happened during the bot's first
  weeks of triage operation.

Why 3: Nobody re-ran the Phase 0d check after the schema drift, so the regex went
  stale silently. The routine produced reports on 2026-05-05/06/07 before the drift
  was significant, and has not been run since the drift became dominant — until today.
  Evidence: stability-reviews/2026-05/2026-05-07-report.md ran 14 days ago.

Why 4: There is no CI / contract test that asserts the Phase 0d awk produces the
  same count as a JSON-parsed reference implementation.
  Evidence: scripts/ directory has no test for the data-adequacy formula.

Why 5: The playbook and the prompt embed the awk inline as documentation rather than
  routing it through a checked-in script. Inline shell snippets cannot be tested.
  Evidence: playbooks/stability-review.md Step 0 has the awk verbatim; the same snippet
  is in stability-review-prompt.md Phase 0d.

Stop condition: Structural — un-tested inline shell embedded in documentation is the
  enabling failure mode; the schema drift was just the trigger.
```
