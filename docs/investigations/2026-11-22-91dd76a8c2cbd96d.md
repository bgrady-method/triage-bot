### Key findings
- runtime-core-api p90 breached 06:31–06:38Z on all four runtime hosts. The 5-min rollup hides it entirely (max 0.59s); at native 10s resolution, 8 points are >2s, peaking at 72.8s.
- Sample traces show the wall-clock time is inside SQL: `SELECT TOP ? [AstOverride] FROM [PreferencesMethod]` 25.2s and `SELECT … accCompany` 6.5s in trace 6b028d870000000033b1f024dde78c16 (43.5s screen load → 408, HeadlessChrome on apexstone public app); `SET CONTEXT_INFO … INSERT INTO [accInvoice]` 17.9s in 6b028c6c00000000be878bdbff0e04e2 (21.7s action, Edge user); `spiderColumns` 9.8s, `spiderDynamicPaging` INSERT 10s.
- Breadth: 91 SQL spans >3s from 7+ services in 30 min, all on cluster 1 (`methoddbclus1` / `sql-prod-1`). Trivial point lookups being slow across unrelated services and tenants means server-side blocking or IO starvation, not a bad query.
- Not Mongo (spans ≤0.01s) and not Redis (0 command errors, 0 timeouts). Redis-cancelled and Mongo-pool-acquire OperationCanceledExceptions are cancellation fallout. Note the keelforce AppEmptyState stack shows a cancel while *waiting for a Mongo pool slot*, which suggests threads were held by the blocked SQL calls.
- Weekly recurrence: the same window had 82 (11-08) and 58 (11-15) slow SQL spans vs 0–3 on weekdays. The monitor cluster fired at the same local time on 11-08, 11-15 and 11-01 (05:45Z, pre-DST), so it follows ~01:30 America/New_York every Sunday. These earlier Sundays fell in the 56-day scheduler gap and the 11-15 fires were triaged individually, which is why it was never connected.
- Real but low-volume user impact: Chrome/Edge/mobile Safari users got 9–40s waits, and at least two 408s and one 400. There's also crawler traffic (AhrefsBot, Googlebot, HeadlessChrome on public apps), which is noise inside the event, not the cause.

### Likely cause
A scheduled weekly SQL Server job on cluster 1 (index rebuild / statistics / CHECKDB / full backup) at ~01:30 ET Sunday blocks or starves ordinary OLTP queries for ~7 minutes. Unconfirmed: the SQL tunnel isn't available, so the SQL Agent schedule and wait stats weren't read.
