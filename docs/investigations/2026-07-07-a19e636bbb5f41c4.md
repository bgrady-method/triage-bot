## Lessons / follow-up
This is a good example of the KB's monitor-id-specific match clause silently going stale when DD recreates a monitor under a new ID — the generic name-text fallback clause (`"contains": "ms-scheduler-api error rate high"`) is what actually caught this occurrence. Worth a standing practice: whenever a monitor referenced by a KB entry's `match.any_of` disappears from a full scan, check whether an identically-named/tagged monitor appeared around the same time and add its ID rather than relying on the name-text fallback indefinitely (fallback matches are the documented false-positive trap in other entries — this is the inverse case, where the fallback was actually correct, but that should be verified each time, not assumed). Also: the KB's declared `evidence_query` aggregate has now returned 0 buckets for 3 consecutive cycles (2026-07-05, 2026-07-06, 2026-07-07) due to a field-name mismatch — this should be fixed in a future stability-review pass rather than continuing to work around it with raw search every cycle.
