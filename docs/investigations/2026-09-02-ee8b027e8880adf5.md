### Key findings
- The APM-level shape (rest-api dominant, GET-tables-endpoint concentration, self-recovering within the monitor's own eval window) is an exact match for this KB entry's documented pattern — 5th confirmed occurrence.
- **New this occurrence:** a wider ES/Logstash sweep (prompted by investigating co-occurring monitor 236570583, see `docs/investigations/2026-09-02-89636a92b60f1520.md`) found log corroboration that every prior investigation of this entry missed. Prior notes checked `service:rest-api status:error env:prod` in **DD Logs** (the Datadog logs product) and got 0 — correctly, since DD Logs never had this data. ES/Logstash (the separate Serilog sink) had it the whole time.
- Root cause, now concrete: account **kuumbamade2** (AccountId 157750) has an external/integration client (`User-Agent: node`) repeatedly calling `GET /api/v1/tables/EdiOrders?filter=id eq '<value>'&top=1` where `<value>` is formatted like `731723-000486` (a PO-number/line-number hyphenated string), against an `EdiOrders.id` column that SQL Server is trying to convert to `int`. Each call throws `SqlException 245` unhandled, surfacing as a 500.
- This is a single-account, single-integration, single-table issue — not infrastructure-shaped, not a platform-wide regression.
- 24h-baseline comparison (25 → 1140 hits) confirms this is a real elevated burst for today, not steady chronic noise.

### Likely cause
A third-party/integration client for account `kuumbamade2` is querying the `EdiOrders` table's `id` field with hyphenated string values (e.g. PO-number–line-number pairs) instead of the integer `id` the column expects, causing a SQL Server type-conversion exception on every call. `Method.Data.RestApi.GlobalExceptionHandler` returns an unhandled 500 instead of a 400, which is what trips the DD monitor's generic 5xx-count threshold.
