### Likely cause
Account portal1gnite's "MNGExport" report is slow/complex enough to exceed the service's 900s render timeout. When the timeout fires, `Thread.Abort()` is issued against the render thread, but the abort cannot reliably interrupt code stuck in native DevExpress/GDI+ calls (`GdipGetFontHeightGivenDPI` et al.) — the thread survives the abort and its memory stays held ("likely stuck in native code"). This happened twice in the same 41-second span (17:39:06Z, 17:39:47Z), consistent with either a retry or a second concurrent request for the same broken report. The resulting thread-pool pressure on the shared `w3wp` worker process on PROD-REPORT-03 is the most likely driver of the process-wide P95 latency spike (peak 73.3s, 14.6x the 5s threshold) that lasted from 17:25Z to 17:39:30Z — a window that also brackets an unrelated `NullReferenceException` for a different account (datamemorysales) during report disposal, itself possibly a symptom of the same resource pressure (native object disposal racing with GC under memory pressure) rather than a fully independent bug.

## Lessons / follow-up
- File a defect against `legacy-reportgeneration-api` / CRM Experience: (1) the `MNGExport` report for account `portal1gnite` needs performance investigation (900s render time is itself alarming, independent of the abort-handling issue); (2) `Thread.Abort()` is not a reliable way to stop native DevExpress/GDI+ rendering calls — a stuck-after-abort thread leaks memory and starves the shared worker process's thread pool for every other caller.
