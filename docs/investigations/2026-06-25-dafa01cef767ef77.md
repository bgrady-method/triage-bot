### Likely cause

**Pattern A (ExportController):** A user ran an export with column mappings that reference non-existent SQL columns. This is either a data integrity issue (fields defined in Method's spider/no-code layer but the SQL column was never created in the tenant DB) or a test scenario with placeholder field names. The 5xx here is user-triggered data error.

**Pattern B (ReviewController):** The `UpdateCell` endpoint at line 114 performs a lookup — likely `WHERE fieldName = @fieldName AND entityType = @entityType AND importSessionId = @importSessionId` — that returns multiple rows when only one is expected. This is a **code defect**: either duplicate rows can exist in the import session's field definition table, or the query lacks a discriminating constraint. The 12-error burst in 12 seconds suggests the user kept clicking while the error repeated.

The two patterns may be from the same user / import session: first tried to export (Pattern A errors), then switched to editing cells in the review view (Pattern B errors). Self-resolved when the user abandoned the session.

## Lessons / follow-up
- **Method.Import.Api `ReviewController.cs:114`** — the LINQ call should use `FirstOrDefault()` instead of `Single()`, or the uniqueness constraint in the backing store should be enforced. Team Admin should file a defect.
- **Structured logging gap:** `method-import-api` does not log the `AccountName` or `importSessionId` in the Serilog properties bag (properties dict was empty in all 19 records). Adding these as enrichment properties would allow immediate account identification on the next occurrence.
- **ExportController 5xx on invalid column names:** The error is surfaced as a 5xx (counted against the APM error rate monitor) but is arguably a 4xx user input validation failure. If ExportController validated the column names before executing the query, these would not trip the P1 5xx monitor.
