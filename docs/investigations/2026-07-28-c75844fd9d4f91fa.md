### Key findings
- The naive bare-text KB match (ki-2026-07-12, keyed only on `monitors/70171778`) does NOT apply this time: rest-api's own 5xx total in the window was 5, all on its normal chronic GET `tables/{table}` resource — no elevation, not the driver.
- The real driver is a tables-fields duplicate-key exception cascade, matching ki-2026-07-09's established signature almost exactly:
  - 24× `System.ArgumentException: An item with the same key has already been added. Key: TeamMultiSelect`, thrown from `Dictionary.TryInsert` in `FieldController.GetFieldNamesWithRestriction` (FieldController.cs:808) — identical method/line to ki-2026-07-09's ShippingAddress occurrence, different colliding key.
  - 15× `System.ArgumentException: An item with the same key has already been added. Key: MultiEntityName`, thrown from `Enumerable.ToDictionary` in the sibling method `FieldController.GetFieldNamesAndTypesFriendly` (FieldController.cs:767) — same unguarded-duplicate-key defect class, different method. Added to ki-2026-07-09's `match.any_of` as a new documented sibling signature.
  - 4× "Failed to SaveViewBundleInternal" with no exception detail captured in these particular records — plausibly ki-2026-07-02 (which explicitly calls out SaveViewBundleInternal 400s) but not confirmed; not attributed to either entry.
  - 2× "FillViewBasicInfo Failed" — `Models.Exceptions.InvalidViewName`, unrelated exception class, minor volume, not investigated further.
- A concurrent gateway 5xx spike (18 errors at 16:38:50Z, the exact same 10s bucket as tables-fields' own spike) is consistent with gateway proxying/counting tables-fields' 500 responses — this explains why the generic cross-service "Unexpected number of 5XX errors" monitor (which sums ALL services) tripped even though no single service crossed an obvious threshold on its own besides tables-fields.
- 0 hits in DD Logs for `service:gateway status:error env:prod` and `service:tables-fields status:error env:prod` — consistent with this being an APM/Serilog-only signal (DD Logs doesn't carry it), same shape ki-2026-07-12 documented for its own (different) signature.

### Likely cause
tables-fields' `FieldController.GetFieldNamesWithRestriction` / `GetFieldNamesAndTypesFriendly` build a field-name/type lookup `Dictionary` (via `Add()` / `ToDictionary()`) without a duplicate-key guard. For accounts whose view/field metadata produces two distinct fields that resolve to the same display/restriction key (this occurrence: "TeamMultiSelect" and "MultiEntityName"; ki-2026-07-09's original occurrence: "ShippingAddress"), the second insert throws `ArgumentException`, which propagates as a 500 and is counted by both the tables-fields-scoped monitor and (via gateway proxy) the generic cross-service 5xx monitor.
