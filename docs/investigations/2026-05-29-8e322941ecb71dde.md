### Key findings
- "JWT Retrieval Failed" is a catch-handler log; the real exception is **System.NullReferenceException** in `MethodSessionService.GetAccountBySubdomain()` on the .NET Framework apps backend (PROD-NEW-04/5/6).
- **100% synthetic**: every one of the 84 failures is a WindowsPowerShell UA from 2 IPs, hitting account id `0` / no-subdomain endpoints. **Zero non-PowerShell (real-user) occurrences.** `GetAccountBySubdomain()` only returns null when there is no resolvable subdomain — which real users always have — so real customers are unaffected.
- Sharp onset ~12:51Z with **no deploy** to any relevant repo, and ms-authentication-api/gateway healthy → the trigger is most likely a **Centreon synthetic-check addition/change** that started probing these endpoints without a valid Host/subdomain, exposing a pre-existing missing null-guard.
- Recurring: 336 over the prior 7 days but 0 in the 24h-ago same-window — it bursts when the probes run, so this is an intermittent, not-continuous pattern.
- The Centreon CRITICALs in this group are the monitor reacting to **its own probe requests failing** with 500s.

### Likely cause
A latent missing null-guard in `Com.Method.ServiceContract.Services.Account.MethodSessionService.GetAccountBySubdomain()` causes a NullReferenceException (surfaced as "JWT Retrieval Failed") whenever an `/apps/api/*` request arrives with no resolvable account subdomain. A synthetic monitoring probe (Centreon, PowerShell, account `0`) started hitting these endpoints at ~12:51Z and now reliably triggers the NRE, generating both the Centreon CRITICALs (this group) and a Datadog Watchdog "New issue to review" (group 25022f8c). No real-user impact observed.
