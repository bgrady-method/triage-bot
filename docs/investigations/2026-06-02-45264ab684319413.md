### Key findings
- **Novel issue, started 2026-06-01 ~07:48Z.** Zero occurrences in the prior 6 days; 17 fires on 2026-06-01, 16 fires on 2026-06-02 by 11:30Z (already on pace to exceed yesterday's count).
- **27 distinct customer accounts** affected over 28h, spread evenly across the two AppRoutine Agent VMs (`ip-172-31-178-173`: 16 fires, `ip-172-31-194-83`: 17 fires). Most accounts hit 1–2 times; the broad fan-out indicates the bug is **not** account-specific data.
- **Root cause is inside `sp_UpdateCustomerItemPurchaseHistory`** on SQL cluster `METHODDBCLUS1` (per-tenant DB). The SP populates a temp table `#PriceAdjusted_…_000001060FFF` and then attempts `CREATE UNIQUE INDEX IX_PA` on the same table — the index creation aborts with SqlException 1505 because the temp data contains duplicate key `(435, 317, 1)` (3-column composite, likely `(CustomerId, ItemId, RecordType)` or similar by shape).
- The duplicate appearing across multiple accounts (the same `(435, 317, 1)` key surfaces in many tenants) strongly suggests **deterministic SP logic producing duplicates** — e.g. a missing `DISTINCT` in the INSERT, or a JOIN whose cardinality recently changed. **Less likely** a per-tenant data anomaly.
- **No deploy correlation surfaced** for `runtime-core` (the C# caller). Because the SP lives in tenant DBs and is updated through a separate migration channel, the trigger event is almost certainly an SP migration / patch deployed around 2026-06-01 07:00–08:00Z. Confirming that requires inspecting the SP version on `METHODDBCLUS1` — out of scope for the bot.
- **NOT ki-24** (RTC p95) — both RTC monitors clean in the window.
- **NOT a DD-monitor-driven alert** — this came from the ES Watcher (B063S8NBW0M) in `#alert-runtime-monitoring`, which watches the ES error stream directly.

### Likely cause
Recent change to stored procedure `sp_UpdateCustomerItemPurchaseHistory` (or to a table/view it joins against) introduced a case where the temp table `#PriceAdjusted` accumulates duplicate rows on the 3-column key `(435, 317, 1)` before `CREATE UNIQUE INDEX IX_PA` runs. The fix is one of:
1. Add `DISTINCT` (or `GROUP BY`) to the INSERT that populates `#PriceAdjusted`.
2. Add `IGNORE_DUP_KEY=ON` to the `IX_PA` index definition (allows silent dedupe — defensible if duplicates are semantically equivalent).
3. Roll back the recent SP migration on `METHODDBCLUS1` (and any other cluster running the same SP) and fix forward.

Affected accounts get their nightly customer purchase-history refresh silently dropped — no immediate user-visible outage, but downstream apps (price-adjusted reports, recurring purchase suggestions) will show stale data until fixed. Sustained at 16/day, ~480/month of failed refreshes.
