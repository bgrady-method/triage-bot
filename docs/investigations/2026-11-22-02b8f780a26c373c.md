### Key findings
- The alert is 2 failed report renders out of about 36 requests. Both failures come from one account (`vpnz`, NZ time zone, `TimeZoneAdjustment=-780`) loading one dashboard (ScreenID1116). Other dashboard reports on the same page loads (opportunities-by-stage / close-ratio / by-user / by-month) rendered 200 and were uploaded to S3.
- The error fires while rows are being *read* (`SqlDataReader.Read` → `DataTable.Load`). That means a varchar→datetime conversion inside the report's view or filter SQL hits a row value it can't convert. The failure is in the query or data, not in connectivity.
- **Hypothesis tested and refuted:** a dd/mm date-literal misparse (NZ locale, day >12). The failing NZ-local days are 28, 16, 18 and 23, but the dashboard also loaded *without* this error on NZ 11-13 (day 13, 11-12 21:56Z). It loaded again cleanly at 11-17 23:33Z, two hours after that day's failure. So the failure isn't a function of the date alone. It is more likely filter- or row-dependent.
- 30-day footprint: 4 episodes, all this signature, 1–2 renders each. The bot has no prior incident-log or investigation record of it.
- No 24h baseline concern. The reportgen error metric was 0 outside the two points.

### Likely cause
A report on vpnz's ScreenID1116 dashboard has a view or filter that CASTs/CONVERTs a varchar column (or a filter value) to datetime. Some rows or filter values can't be converted, so SQL Server raises error 242 and ReportGenerationAPI returns 500. The user sees one broken dashboard tile. The account is a customer, the problem is data-shaped, and it doesn't extend beyond that account.
