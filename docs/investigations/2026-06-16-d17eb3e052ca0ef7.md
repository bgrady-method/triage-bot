### Key findings
- **Throughput collapse (the access outage):** runtime-core-api request volume dropped ~50% from ~1500 hits/10m (05:00–06:00Z) to ~544–750 hits/10m starting **06:20Z**, persisting through ~10:00Z. A throughput drop = requests not completing → users unable to load/enter Method ("signin not possible"). Onset aligns with the customer-reported "started around 2:00am" (06:00Z).
- **Error rate elevated, never cleanly paged:** runtime-core-api error rate ran 1.5–3.6% through the incident (peaks 06:30Z 3.43%, 08:40Z 3.57%, 09:00Z 3.07%, 09:10Z 3.29%), only breaching the 5% monitor (17420774) threshold at **10:04Z** — which is *why no Datadog page fired during the 4-hour customer-facing window*. 5XX absolute count: 424 over window, all dominated by runtime-core-api.
- **Recovery signature pins the fix:** at **10:00Z** throughput rebounded 996 → 3128 → 6130 → 5941 → 8904 hits/10m and error rate fell to 0.13% (10:00Z) → 0.00% (10:20Z). This is *exactly* when Arash recycled the backend application pools (#swat message 10:05Z: "I've recycled some of our backend application pools, and it seems the errors in Logstash are winding down"). The pool recycle drained the blocked traffic and restored service.
- **Auth layer was healthy:** the Datadog synthetic "[Synthetics] Sign in to Method" (monitor 127198928) did NOT fire during the incident (last trigger 20:11Z the prior day), and ms-authentication-api/oauth2 had negligible 5XX. The failure was **post-login runtime-core degradation**, not an auth/sign-in-flow break — users perceived it as "can't sign in" because they couldn't get into the app after authenticating.
- **No deploy correlation:** no engineer named a deploy or rollback in #swat (Arash attributed to pool state). Method deploys via Azure DevOps/TFS so `gh` shows nothing. Treat as resource exhaustion, not a code regression.
- **Separate minor item (do not conflate):** Arash noted at 10:35Z that Avast delisted `miurl.cc` (Method's URL shortener, `legacy-miurl-api`) from its threat-detection list. This is a distinct issue handled in the same #swat session; it would block miurl links in AV-scanned email but does not explain a runtime-core throughput collapse and was not fixed by the pool recycle.

### Likely cause
runtime-core-api backend IIS application pool(s) entered a degraded state around 06:20Z — consistent with gradual resource exhaustion (thread-pool starvation or memory pressure), since the degradation built over hours rather than appearing instantly and was cleared by a pool recycle with no code change. The pool stopped servicing requests at normal capacity (throughput halved) and shed a fraction as 5XX. Recycling the pool (~10:05Z) immediately restored throughput and dropped errors to baseline. The specific upstream trigger (what exhausted the pool — a slow dependency, a hot account/routine, a leak) is **undetermined** because the Serilog→Elasticsearch log sink has been returning 401 for ~16 days, leaving no application-level exception/stack visibility during the incident.
