### Key findings
- **Root symptom:** `error: 40 (TCP Provider) — Could not open a connection to SQL Server` on `sql.connection_c2`, `c3`, `c4` from prod-rt-01. Error 40 is a **TCP-level reachability failure** (host/network/DNS), not auth or login — the SQL endpoints for clusters 2/3/4 were unreachable, ~15s connect timeout each.
- **Intermittent/flapping, not clean hard-down:** health probe at 02:17:05Z reported all 5 SQL connections Healthy, yet journal shows failures at 01:40–01:50 and again 02:14–02:16. c1 and c5 never reported unhealthy.
- **Cascade correlation (single root cause):** timeline lines up — mobile-notif 01:26Z → auth/identity 5xx ramp + 5XX monitor 01:36–01:39Z → designer SQL c2/c3/c4 01:40–01:50Z → scheduler 01:44Z → rt-core-subscriber stall 01:52Z → search 02:03Z → gateway/auth/identity P95 02:11–02:16Z. Every service in the cluster is a SQL consumer.
- **Highest user impact is auth, not runtime-designer:** ms-authentication-api + ms-identity-api are critical-path (per CLAUDE.md, auth down → all NEW sessions fail; existing JWTs valid until expiry). Both are still throwing 5xx at 02:22Z.
- **The restart did not help and briefly made it worse:** designercoreapi hung on startup (health timeout, http 000 at 02:17:55Z) — it blocks on SQL during init. It resumed serving 2-4 hits/30s by 02:20-02:22Z, consistent with SQL becoming intermittently reachable again rather than the restart fixing anything.

### Likely cause
Loss (or severe intermittency) of TCP reachability from the prod app tier to SQL Server clusters **c2/c3/c4** starting ~01:26–01:40 UTC — most consistent with a SQL-tier or network-path event (SQL host(s) down/restarting/overloaded, a security-group/firewall/route change on the app→SQL path, or DNS for the SQL endpoints), **not** a code deploy (no deploy signal; error is TCP-40 reachability across multiple independent services). Cascades as 5xx/latency into every SQL-dependent service, with auth/identity (critical path) taking the largest hit.
