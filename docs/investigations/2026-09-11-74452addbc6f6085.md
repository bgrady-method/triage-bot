### Key findings
- **Real, reproducible code defect**, not monitoring noise. Both exception types occurred on the same endpoint (`RequestPath: /v2/suggestions`) with an **unresolved account context** (`AccountId: 0`, `AccountName: None`, `TenantId: 0`).
- Full stack trace on one sample:
  ```
  System.InvalidOperationException: No authenticationScheme was specified, and there was no DefaultForbidScheme found.
  The default schemes can be set using either AddAuthentication(string defaultScheme) or
  AddAuthentication(Action<AuthenticationOptions> configureOptions).
     at Microsoft.AspNetCore.Authentication.AuthenticationService.ForbidAsync(HttpContext context, String scheme, AuthenticationProperties properties)
     at Microsoft.AspNetCore.Authentication.AuthenticationServiceImpl.ForbidAsync(...)
     at Microsoft.AspNetCore.Mvc.ForbidResult.ExecuteResultAsync(ActionContext context)
     at Microsoft.AspNetCore.Mvc.Infrastructure.ResourceInvoker...
  ```
- Interpretation: when a request to `/v2/suggestions` arrives without a resolvable account/tenant context, the authorization pipeline attempts to return a `403 Forbid` result, but ms-tags-api's ASP.NET Core auth configuration has no default `ForbidScheme` registered — so instead of a clean 403, the app throws an unhandled `InvalidOperationException` (likely surfacing as a 500 to the caller). The 2 "Account Access Denied" log lines are almost certainly the same underlying request pair, logged at a different layer before the crash.
- Only 4 occurrences in the 30-min window, no prior history for this exact signature (monitor has fired twice before, both >30 days ago, neither with this signature per available incident-log data).

### Likely cause
`ms-tags-api`'s authentication/authorization startup configuration is missing a `DefaultForbidScheme` (or equivalent `AddAuthentication`/`AddAuthorization` wiring), so any request that should cleanly 403 (e.g., an unauthenticated or cross-tenant call to `/v2/suggestions`) instead throws an unhandled exception.
