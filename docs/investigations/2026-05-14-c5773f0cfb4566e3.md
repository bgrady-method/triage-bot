- **Signin failures were partial, not total:** Inder could sign in while Nelson couldn't at the same moment (07:55 EDT). This is the canonical pattern of a Redis JWT-cache hiccup or a partial back-end pool failure (some IIS workers OK, others not), not a complete `ms-authentication-api` outage.

### Likely cause
Shared upstream infrastructure failure affecting both `ms-tables-fields-api` (QBO accounts only — QBDT path stayed up) and the auth path simultaneously. Top hypotheses in priority order:

1. **SQL cluster blip on the QBO/auth-shared cluster.** QBO accounts are typically on a specific SQL cluster (one of C1–C5 per `04-databases.md`). If that cluster's primary failed over or had a brief network partition, both QBO tables-fields queries (spider* tables) and any auth lookups against per-tenant data on that cluster would fail simultaneously. QBDT accounts on a different cluster would be unaffected — matches the QBDT-still-works observation. AlocetSystem (`SQL_DATABASE` secret) lives on prod1; if prod1 was the affected node, signin lookups would partially fail too.
2. **IIS `microservices` pool recycle.** Tables-fields runs in the `microservices` IIS pool (per CLAUDE.md). A pool recycle would knock out tables-fields for ~30–90 s. But this alone wouldn't explain signin failures (ms-authentication isn't on `microservices`). Possible if combined with a Redis JWT-cache miss spike at the same time.
3. **Redis hiccup.** Would cause every gateway request to fall through to `ms-authentication` (uncached JWT path) and the resulting latency spike could fail-open as 500s. Doesn't easily explain QBO-only scoping of T&F failures.
