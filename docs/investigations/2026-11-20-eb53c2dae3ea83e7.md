### Key findings
- A mass SMS send at ~15:04Z produced a burst of Twilio status callbacks (`POST /v1/sms/status`). The service took ~6x its normal request rate and ~40x its Redis command rate for two minutes.
- 9 Redis command errors (~0.1%) during the burst crossed the 227940275 **warning** threshold (5) but not critical (10). Redis latency stayed in single-digit ms and host memory is healthy, so this isn't a Valkey or host problem.
- **The more important finding is a real concurrency bug.** `Twilio.Security.RequestValidator` wraps a single `HMACSHA1` instance and isn't thread-safe. `TwilioApiProvider.ValidateSessionAsync` (line 122) evidently shares one validator across concurrent requests (singleton provider or static field). Under concurrent callbacks the HMAC throws, signature validation fails, and legitimate Twilio callbacks are rejected. SMS delivery-status updates are probably lost. It's chronic: 50 in 7 days, clustered on bursts.
- I couldn't attribute an account or user count (Twilio callbacks carry no `@account_name`).

### Likely cause
A traffic burst from a bulk SMS send. The Redis errors are a minor side effect of the load. Underneath it, a thread-unsafe shared `Twilio.Security.RequestValidator` makes concurrent status-callback validation throw.
