### Likely cause
Account **stellarair**'s spider metadata (the `spider*` field/table-relationship rows owned by ms-tables-fields-api) has one or more linked fields on the `Activity`/`ActivityJobItems` view family with a null `FieldTableNameRef`. When the App Update pipeline pushes a view/field-bundle update for that account (`SaveViewBundleInternal` → `UpdateViewWithRollBack` → `GetView` → `GetFieldList` → `GetAllFields` → `GetAllFieldsInstall` → `GetColumnForAllFields`), the metadata walk throws `ArgumentNullException` on the null-ref field, and `SaveViewBundleInternal` reports a 400 for the whole app rather than skipping just the bad field. This is a per-account data-integrity condition (bad/incomplete spider metadata), not a service-wide regression — the fix likely needs both (a) a data repair for stellarair's `spiderFields` rows on the affected fields, and (b) a defensive null-check in `MetadataDataProvider.GetColumnForAllFields` (MetadataDataProvider.cs:1087) so one bad field doesn't fail the entire view-bundle save. Code-level confirmation blocked by the GH access gap (see below) — this diagnosis is built entirely from the ES stack trace, not source inspection.

## Lessons / follow-up
- This exact error shape (`FieldTableNameRef Is Null` → `GetColumnForAllFields failed` → `SaveViewBundleInternal` 400) has now been independently investigated twice from scratch (2026-05-28 and today) without a KB entry existing in between — a month of repeat investigation cost for a pattern that was diagnosable the first time. Closing that gap is the main point of this cycle's KB write.
- `match_kb.py`'s `contains: "tables-fields"` clause on `ki-windows-patching-app-pool-needs-recycle-no-reboot` is overly broad and false-positives on any tables-fields-related alert (this is now the second time this class of match-clause bug has been observed — see the 16:29Z cycle's identical note about miurl-agent false-positiving onto `ki-2026-06-16-miurl-shortlink-domain-unreachable`). Recommend tightening both `any_of.contains` clauses to something more specific (e.g. `PL-44252` alone for the Windows-patching entry, since that Jira ID is a much stronger signal than the bare service name).
- DD Logs (`dd_search.py logs`) returns 0 for `service:tables-fields` regardless of query — this service's structured logs only reach ES/Serilog, not DD Logs. Future tables-fields investigations should go straight to ES and skip the DD Logs step.
- Recommend Admin team: (1) data-repair pass on stellarair's `Activity`/`ActivityJobItems` linked-field metadata (and audit for other accounts with the same null `FieldTableNameRef` condition, since this has now hit 2 different accounts in 5 weeks), and (2) a defensive null-check in `MetadataDataProvider.GetColumnForAllFields` so one bad field degrades gracefully instead of failing the whole view-bundle save for the account.
