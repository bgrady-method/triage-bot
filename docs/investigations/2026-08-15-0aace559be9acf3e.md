### Key findings
- The monitor's `@account_name:sommselection` group crossed the >40-in-5min threshold, but **100% of the sommselection-attributed errors trace to a single bot-crawler session** (bingbot/HeadlessChrome UA, one IP, one `session_id`) hitting the analytics-beacon endpoint `/api/analytics/user/Event`, not a real-user-facing failure.
- `http.status_code: 0` + `error.origin: network` is a client-side network-layer failure (request never got a response) — consistent with a headless/automated client whose environment doesn't complete the beacon `fetch`/`XHR` (blocked, aborted, or no real network stack), not an application or server-side bug.
- This is mechanistically **unrelated** to the chronic `ki-2026-05-21-gateway-microservices-timeout` pattern (Ocelot/`ms-gateway-api` timeouts on `GetSyncWidgetInfoAsync`), even though the monitor's generic alert title text superficially matches that KB entry's bare `contains` clauses. The other 109/200 sampled logs in the same window *do* show the normal diffuse `ki-21` shape on unrelated accounts — that chronic pattern is still present and unremarkable in this window, it just isn't what tripped this specific account group.
- Zero real customer impact: one automated crawler session against one tenant's portal, not a production incident.

### Likely cause
A search-engine/automated crawler (bingbot UA, Azure-hosted IP) indexed or probed `sommselection.methodportal.com`, and the app's client-side analytics beacon (`/api/analytics/user/Event`) fired repeatedly during that crawl but failed at the network layer for every call (headless/bot client environment, not a real browser network stack) — tripping the per-account XHR-error-count monitor purely on beacon-call volume from one non-human session.

## Lessons / follow-up
- Naive KB text-matching on this monitor's alert title is unreliable — the title is identical (`"Unusual number of XHR errors for account: {{name}}"`) regardless of which of at least two unrelated mechanisms triggered it (chronic Ocelot gateway timeout vs. this bot-crawler analytics-beacon noise). Any future investigation of an `Unusual number of XHR errors` alert should re-verify the account-level log breakdown before accepting the `ki-2026-05-21` match, not just the bare monitor-id/title text.
- Worth flagging to Admin/Growth: the analytics-beacon endpoint executes for non-authenticated/bot crawler sessions and has no timeout/retry hygiene visible in the failure signature (`status_code:0`, "Failed to load") — gating the beacon call on a real user session, or excluding `http.status_code:0` network-layer failures from this monitor's XHR-error count, would prevent bot traffic from tripping a production-facing monitor at all.
