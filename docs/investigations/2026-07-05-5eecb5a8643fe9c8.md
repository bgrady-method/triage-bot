### Key findings
- A genuine, independently-corroborated (DD APM **and** ES/Logstash) telemetry-and-traffic silence affected **ms-authentication-api** for ~3.5h (01:06–04:36Z) and **ms-tables-fields-api** for ~2h (02:00–04:00Z), both recovering with a burst of activity/catch-up right as the gap ends.
- **Gateway and runtime-core-api did NOT show the same gap** — both had continuous log/trace volume throughout, and gateway showed zero error-level logs despite its own 5xx/P95 monitors firing. This rules out a whole-stack outage; the affected set looks scoped to services fronted by `microservices.methodlocal.int` (ms-authentication-api, ms-tables-fields-api, and by monitor-tag pattern likely ms-preferences-api, ms-account-api, ms-search-api, ms-identity-api, method-import-*, services/authservice, signin, signup, oauth2.identity.server — the entire `team:admin`-tagged monitor set, 25 distinct monitors, all clustered 04:36–05:20Z).
- Additional, less-conclusive corroboration: the same "no-traffic/5xx/P95" signature also appears in the same window across `team:vae` (ms-documents-api, ms-tags-api, miurl-agent — 5 monitors), `team:first-strike` (ms-account-api, runtime-core-api, signup — 6 monitors), and `team:devops`/EDA (3 monitors) — a total of 51 distinct monitor fires across 6 different DD team tags in essentially the same ~45-minute window, which is a very low-probability coincidence if these were independent, unrelated blips.
- A **second, smaller recurrence** ~07:00–08:41Z hit ms-account-api (log volume dropped from 1133/hr to 2, then 0, before partially recovering to 102/hr — still below baseline) plus designer-core-api, EDA Kafka/ingest, and a second ms-account-api P95 monitor — consistent with the same underlying instability flickering again rather than a fully independent second incident.
- No elevated error-rate anywhere that was checked (gateway, ms-authentication-api, ms-account-api, tables-fields, eda_consumer, ms-scheduler-api all returned 0 `status:error` hits in ES for this window) — this looks like a **silent availability/telemetry gap**, not an error-throwing incident. Consistent with either (a) the affected hosts/site being genuinely unreachable (which would silence both log shipping and trace submission simultaneously) or (b) a shared telemetry-pipeline disruption that happened to align with genuinely low overnight traffic.
- Existing sessions were very likely unaffected: per CLAUDE.md, `ms-authentication-api` down only blocks **new** sessions/token refresh — cached JWTs via Redis keep existing users working, consistent with gateway's continuous healthy traffic throughout.

### Likely cause
Most probable hypothesis: the `microservices.methodlocal.int`-hosted tier (or the host(s)/VM(s) backing it) was unreachable or degraded for ~3.5 hours overnight (2026-07-05 ~01:06–04:36 UTC, with a shorter ~1h recurrence ~07:00–08:00 UTC), silencing both Datadog APM trace submission and Elasticsearch/Logstash log shipping for the services it hosts (ms-authentication-api, ms-tables-fields-api, and likely the broader team:admin-tagged fleet), while gateway and runtime-core-api — hosted separately — continued serving traffic normally via cached JWTs. A maintenance/patching window is plausible given the timing (overnight, self-resolving, no errors). Cannot rule out a narrower "telemetry pipeline only" explanation (DD Agent or Logstash sink outage without real service impact) given the total absence of corroborating application errors.
