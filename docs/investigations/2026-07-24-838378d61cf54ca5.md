### Key findings
- **The 55,849-second p95 datapoint is a far more extreme outlier than the 2026-07-13 occurrence (1578.86s) that first broke this KB's "cleanest non-reproduction pattern" framing.** Per this KB entry's own playbook step 4 — *"If a 3rd occurrence ever shows a genuine elevated p95, treat as a break from this pattern and escalate immediately rather than assuming noise"* — this is escalated rather than mechanically suppressed.
- **Working hypothesis (unconfirmed): APM span-duration artifact, not a real latency regression.** `notifications` runs SignalR Hub connections; if `trace.aspnet.request` instruments the underlying HTTP/WebSocket upgrade request, a long-lived Hub connection's "request duration" is only recorded when the connection finally closes — so a connection open for ~15.5h would produce exactly this shape (single-bucket, multi-thousand-second outlier, pristine surrounding baseline, 0 errors). This is consistent with both this occurrence and the 07-13 one (1578.86s ≈ 26min, also plausible as a shorter-lived connection).

Comparing today (~45k/24h) against the prior day (~60k/24h) shows this is **chronic baseline noise, not new today**, and the volume trend (lower today, not higher) argues against a fresh reconnect-storm causing today's specific outlier.
- 0 Error-level logs, 0 `status:error` DD logs — no corroborating application failure.

### Likely cause
Most likely an APM instrumentation artifact from a long-lived SignalR/Hub WebSocket connection closing (unconfirmed — would need the notifications-service team to confirm how `trace.aspnet.request` spans are scoped for Hub connections). Not believed to be a real per-request latency regression given the pristine surrounding baseline and zero error corroboration.
