### Key findings
1. **Root cause is gateway-side timeout while proxying to `microservices.methodlocal.int`.** Frontend `XHR error / status_code:0 / "Failed to load"` is just the symptom — the actual failure is in `ms-gateway-api`'s Ocelot middleware, which gets `TaskCanceledException` after the default request timeout while waiting for the .NET Framework microservices pool to respond.
2. **Multi-path, multi-account.** Slow paths span at least four owned services (sync-util, preferences, account, plus several syncwidget account variants). This points at the **shared upstream** (the `microservices` IIS app pool / site) being the bottleneck, not any single microservice.
3. **Volume is identical to 24h-ago baseline.** 1072 vs 1064 Ocelot warnings → +0.7%. **This is chronic background noise, not an active incident.** The XHR-error monitor (77419271) crosses its >40/5m per-account threshold whenever a single user triggers many widget loads while the gateway is in its usual marginal state — meaning *random per-account fires are expected as long as the underlying timeout pattern persists*.
4. **No deploy correlation.** Locally cloned gateway/method-ui/legacy-syncservice repos all flat for 7+ days. This is a sustained operational condition, not a regression.
5. **Bot is partly blind to alert subject.** As with Groups A and B, Slack MCP doesn't surface the block content of monitor 77419271's Slack notification (which contains the `@account_name`). We can identify the monitor by `last_triggered` cross-correlation but we cannot enumerate which specific accounts each of the 4 alerts pinned to. Best-guess top account this window: `homewatchofct` (12 XHR errors).

### Likely cause
**ms-gateway-api → microservices.methodlocal.int request timeouts** are happening at a steady-state rate of ~15/min, driven primarily by slow responses from the .NET Framework `microservices` IIS pool. Multiple paths (syncwidget, preferences/v3/User, account/banners/queue, account/learning/progress) are affected, which rules out a single misbehaving microservice and points at pool-level latency (memory pressure, slow SQL on shared connection pool, or long warmup after recent recycle). When a user's session triggers several syncwidget loads in <5 min and they all time out, monitor 77419271 trips — but the underlying state has been present for ≥24h.
