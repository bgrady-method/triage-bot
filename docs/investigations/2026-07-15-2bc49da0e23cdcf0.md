### Key findings

1. **The trigger is a single template-app push.** `App Publish - Started - Push Update [App: "Sales Orders", AppId: 55b7fa26-9d45-400d-829f-a3610098567c, Version: 182, JobId: d055f8dd-9bb5-4996-9d71-dd7bae39c557, Publisher: "templatedevv2"]` at **13:13:13.53Z**. The first `Failed to SaveViewBundleInternal` in tables-fields lands **3.7s later at 13:13:17.21Z**; the first Slack failure at 13:13:15Z. tables-fields p95 first breaches the same minute (13:13:00Z).

2. **Fan-out scale:** the push targeted ~5,571 subscriber accounts in ~27 minutes (13:13→13:40Z), driving tables-fields to **4.5× its normal request volume** (58,036 vs 12,817 for the same window yesterday) with `saveviewbundleinternal` p95 at **10.7s**.

3. **The functional bug — deterministic, not load-related.** 196 accounts failed with HTTP 400 / `ErrorCode 50`: *"The field 'Name' already exists. Please change the spelling and try again."* on view `InvSalesOrderRevertReason`. This is a validation rejection, not a timeout — it would fail at any load level.

4. **Partial application (the most serious consequence).** The API response body in the alerts shows the bundle applied *split*:
   - `SuccessfulBundle`: `viewPreferencesMethod` → field `DefaultInvSalesOrderRevertReason` **created**
   - `UnSuccessfulBundle`: `InvSalesOrderRevertReason` → **failed** (`The field 'Name' already exists`)
   - `GeneratedViews`: `["main:PreferencesMethod"]`

   So on those 196 accounts the *preference pointing at* the revert-reason table was written while the *table itself* was not created. The bundle is not applied atomically and there is no rollback on partial failure.

5. **Redis is an effect, not a cause.** First `SaveViewBundleInternal` failure **13:13:17.21Z**; first `Redis Cache Circuit Breaker OPENED` **13:13:27.74Z** — **10 seconds later**. All 11 circuit-breaker opens (13:13:27→13:38:20Z) sit *inside* the push window. Redis command errors are **41 from tables-fields and 0 from runtime-core-api**. The cache pressure was produced by the request storm.

6. **RTC Screen Load is independent chronic noise, not blast radius.** Monitor 115456700 triggered at **13:05:25Z — 8 minutes before the push began** — and is *still* breaching at 14:51Z (peak 8.50s) while tables-fields is fully recovered (0/180 buckets >1s after 14:00Z). This is `ki-2026-05-24-runtime-core-rtc-p95-recurring` (occurrence #238), which has 237 prior occurrences and fires independently. **Do not attribute it to the push.**

7. **Recovery:** tables-fields fully recovered by 14:00Z (peak 0.62s, 0 buckets over threshold). No downstream errors referencing `InvSalesOrderRevertReason` after 13:40Z (0 hits) — the partial schema state is not yet producing customer-visible errors *in logs*, but that is not proof it is harmless (see gaps).

8. **This is a repeat pattern, escalating.** Only 3 app publishes in the last 7 days. The prior `Sales Orders` **v181** push (07-08 16:13:54Z, job 1e302df5) also stormed tables-fields: 15,294 hits / p95 peak 1.57s / 1 bucket >1s. Today's v182 was **3.4× larger** (51,919 hits / p95 3.25s / 57 buckets >1s). Mass push-update fan-out routinely generates a latency storm; it crossed alerting thresholds this time.

### Likely cause

The `Sales Orders` template app **v182**, published from `templatedevv2` at 13:13:13Z, introduces a new view/table `InvSalesOrderRevertReason` plus a `DefaultInvSalesOrderRevertReason` preference field. On ~196 of ~5,571 subscriber accounts the bundle's declared field `Name` collides with a `Name` field that already exists on that view, so `ms-tables-fields-api` rejects the view with HTTP 400 / ErrorCode 50 and the app update fails for those accounts — leaving the preference field created but its target table missing. Separately, the un-throttled ~5,500-account fan-out drove tables-fields to 4.5× normal volume, which produced the tables-fields p95 breach (monitor 299251779) and the Redis circuit-breaker/error monitor (227940275) as collateral.

**Confidence 0.88.** The trigger, timing, scale, failure mode, and blast radius are all directly evidenced. What is *not* established: **why** those specific 196 accounts already have a `Name` field on that view.

## What we couldn't determine

- **Why those 196 accounts collide and the other ~5,375 don't.** Two candidate mechanisms, not distinguished: (a) new-table bootstrap auto-creates a default `Name` field which the bundle then re-declares, racing only where the table is created fresh; (b) those accounts carry a pre-existing customization or a leftover `InvSalesOrderRevertReason` table from an earlier partial run. Distinguishing them needs a tenant-DB read (`sql_query.py`/`mongo_query.py`), which is SSH-bastion-gated and was not run this cycle.

## Lessons / follow-up

1. **Bundle application is not atomic.** A partial failure leaves the preference field written and its target table absent. Either apply the bundle transactionally or roll back `SuccessfulBundle` entries when any `UnSuccessfulBundle` entry exists. This is the highest-value fix and is owned by `CRM Experience`.
2. **Push fan-out is unthrottled.** ~5,500 accounts × bundle-save in 27 min = 4.5× baseline load on a critical-path service. v181 did the same at 1/3 scale a week earlier. Rate-limit or stagger the consumer; this will recur on every template-app publish and grows with the subscriber base.
3. **The 196 failed accounts need reconciliation** — they are on v181 content with a v182 preference field. Re-running the push will not fix them; it will hit the same collision.
4. **Alerting gap:** there is no monitor on app-update job failure rate. 196 accounts failed and the only signal was 174 individual Slack messages plus three *collateral* monitors that all point at the wrong service. A `sum:app-update failures by JobId` monitor would name the actual culprit in one line.
5. **KB hygiene:** three entries bare-match this incident's monitor ids and all three are wrong. Precedence notes added to the two Redis-mechanism entries so the next cycle checks ordering (blip-before-spike vs spike-before-blip) and service attribution before matching.
