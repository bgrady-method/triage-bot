### Key findings
- Sample stack: `AbortError: signal is aborted without reason at Object.cancel <- i._remove <- a._updateStyle <- a.setStyle <- a.remove` (mapbox-gl, `vendor.min.js`), called from `m-one.vendor.min.js`. The map instance is being removed and cancels its own pending style fetch. RUM records the cancelled fetch as a status-0 network error.
- This is client-side self-cancellation. It is not a Mapbox outage, a token problem, or a Method backend failure. There are 0 server-side errors and 0 other XHR errors for the account.
- One session produced about 81 map teardowns in roughly an hour. That suggests the m-one map widget on that screen remounts repeatedly (a possible re-render loop). It is cosmetic for alerting, but a real frontend inefficiency.
- Extrapolation: not warranted. One account, one user session. Other accounts see the same AbortError at low single-digit-per-hour rates, well below the monitor threshold.

### Likely cause
The m-one map control on a haydenfire1 screen was torn down and recreated repeatedly in one user session. Each `Map.remove()` aborted the in-flight `streets-v11` style request. RUM counts each abort as an XHR error, and 25+ in 5 minutes tripped the per-account Warn.
