## Lessons / follow-up
- **`git fetch` per cycle paid off.** Cycle 4's recommendation was acted on. Without it, the routine never would have seen the 8 PRs deployed in the alert window. **Make this permanent** — add `git -C <repo> fetch --quiet` to the step-4 deploy-check sequence in `prompt.md`, OR add a `git fetch --all` to `scripts/run-routine.ps1` so it happens before the routine starts each cycle.
- **The "self-resolved" call in cycle 4 was wrong.** 72-min quiet was not resolution. The bot should not infer resolution from a single multi-cycle quiet — only a human ACK or a confirmed Datadog monitor-resolved event should change the active-incident assessment. Consider tracking a "last_resolved_ts" per fingerprint.
- **`group_window_minutes=30` still splits this incident.** Five cycles, gaps of 34/14/5/72 min. No fixed window resolves this cleanly. A better fix is to introduce **fingerprint-level escalation**: when N consecutive groups share the same (channel, bot, text_fingerprint) within 24h, switch to a single rolling DM thread instead of one DM per group. Documented in cycle 4; restating because it's now even more obvious with cycle 5.
- **Five DMs in <4h for one incident with no human action between them.** The bot is generating noise without driving action. Either (a) the DMs aren't reaching Ben (notification config?), (b) Ben is aware but waiting for working hours, or (c) the recommended actions aren't strong enough to compel a response. Worth a real conversation with Ben on cadence and what *would* prompt action.
- **DD/ES creds still missing for the 5th cycle in a row.** Auto-investigation is fundamentally degraded; routine value = pattern recognition only. Wiring secrets must happen for this routine to be useful beyond "your channel is still loud."
