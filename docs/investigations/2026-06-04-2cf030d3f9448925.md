### Key findings
- **The 13:12Z DM's "no deploys 48h" hypothesis was wrong.** The bot's deploy check only ran against cloned repos (runtime-core, m-one, tables-fields, api-gateway, etc.); ms-account-api is not cloned, so its 12:30Z release was invisible to the prior cycle. **Operators identified ms-account-api as the deploy correlation** at 13:27Z.
- **Issue onset matches deploy + 20 min** (12:30Z deploy → 12:50Z issue start per Gozde, 12:52Z gateway 5XX surge per the 13:12Z investigation). The 20-minute lag is consistent with cold-start / cache-warming / connection-pool exhaustion in a regression.
- **Rollback (preferences first at 13:15Z, then "everything released today" by 14:00Z) DID NOT resolve.** This is significant — implies either (a) rollback was incomplete / didn't catch ms-account, or (b) the root cause is something downstream that the deploy merely triggered (corrupted state, leaked connections, queue backlog).
- **Yuri began reverting ms-account specifically at 14:03Z** — explicit operator action targeting the suspect.
- **Failure mechanism: runtime-core spamming preferences.** Gozde at 13:30Z: "Runtime had 90K calls to preferences in the last 30 mins. Currently returns 502 bad gateway." This is the path: runtime-core → ms-preferences-api (or ms-account-api affecting preferences) returns 502 → gateway timeouts → frontend XHR errors.
- **Currently still firing as of 14:09Z**: Redis Errors High, 5XX errors, RTC Screen Load p95, RTC Action Execution p95, XHR errors, ms-account-api avg latency. The outage is **not yet contained**.
- **Impact is broad, not single-account.** 30+ distinct accounts in 50 XHR error samples. Extrapolation: cluster_lower_bound across at least the impacted clusters (`prod3/4/5` per account_impact wrapper's unconfigured-clusters output — suggests gateway-shaped, not per-tenant).
- **Status page itself failed during the incident** (Inder 13:36Z, 13:44Z): a meta-impact — customers had no way to learn what was happening. Intercom status message used as fallback at 14:06Z.

### Likely cause
A regression introduced by the ms-account-api release at 12:30Z UTC propagated to preferences/runtime call paths within ~20 minutes, causing ms-preferences-api to return 502s and the ms-gateway-api Ocelot proxy to time out on `microservices.method.int` (same shape as ki-21 chronic, but with ~100x magnitude driven by this deploy). The simple deploy revert did not resolve, suggesting either: incomplete rollback, downstream state corruption (e.g., poisoned Redis cache, stuck RabbitMQ queue, leaked connections), or a config-side change that the code revert did not undo. Operators are now (14:03Z) targeting ms-account specifically.

1. **Add ms-account-api and ms-preferences-api to `routines/triage.yaml` `repos:`** so deploy-correlation checks catch them. The prior cycle's "no deploys 48h" finding was wrong specifically because of this gap.
2. **The deploy check is the highest-leverage signal for surge-magnitude incidents.** A KB shape match (ki-21) led to a low-confidence "chronic recurrence" framing in the original DM, even though the magnitude was unprecedented. The +2 novel_no_prior_24h signal and +3 metric_breach (98x) flagged it correctly, but the matched_kb tag created cognitive friction. 3. **`account_impact.py` is blind to prod3/4/5.** Either configure those cluster creds for the routine, or have the wrapper degrade more gracefully (today: returns `not_found`, which the bot treats as "drop"; better: return `tenant_unreachable` so the cluster_lower_bound fallback is wired up).
4. **Status-page failure during the incident** is a customer-facing reliability issue separate from the platform outage. File a follow-up: status.method.me should be hosted/cached independently of the production stack.
5. **Add an inhibition signal "operator-confirmed-different-root-cause-from-matched-KB"** — when #swat operators name a service NOT in the matched_kb playbook, that's strong evidence the KB hypothesis is the wrong framing.
